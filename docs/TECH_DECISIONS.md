# 기술·설계 결정

personal-english MVP를 만들 때의 고려사항과 언어·프레임워크 선택 근거.

## 1. 만들 때 무엇을 고려해야 하는가

### 제품·학습 UX

- **진단 3축**(단어 / 문장 구조 / 소리)을 UI에서 어떻게 구분·기록할지 — 자기 보고 vs 퀴즈 보조.
- **끊김 지점**을 시간축(오디오) 또는 문장·구간 단위로 표시하는 방식.
- Duolingo처럼 **짧은 일일 세션**(5~10분)으로 끝낼 수 있는지.
- 같은 passage에서 **듣기 vs 읽기** 결과를 비교해 “읽으면 되는데 듣기만 안 됨” 패턴을 남길지.

### 오디오·미디어

- 모바일 Safari 포함 **브라우저 오디오** 제약(자동 재생, 백그라운드).
- 구간 반복, 속도 조절(0.75x~1x)이 핵심 기능인지.
- STT/TTS를 쓸 경우 **비용·지연·오프라인** 트레이드오프.

### 데이터·프라이버시

- 1인용 앱 → **로컬 우선** 저장(세션, unknown words, 약점 통계).
- 나중에 기기 간 동기화가 필요해지면 그때 auth/백엔드 추가.
- 학습 로그에 **개인 식별 정보**를 넣지 않기.

### 콘텐츠

- passage 스키마(텍스트, 오디오 URL, 난이도, 출처).
- 저작권·출처 표기, 시드 콘텐츠 10~20개로 MVP 검증.

### 엔지니어링

- **MVP는 한 가지 시나리오**만 end-to-end (예: passage 1개 → 구간 표시 → 원인 태그 → 미니 드릴).
- 핵심 플로우 **E2E 테스트** 1~2개.
- 접근성: 전사(transcript), 키보드 조작.

## 2. 어떤 언어로 작업하는가 — **TypeScript**

| 이유 | 설명 |
|------|------|
| 한 코드베이스 | UI(React)와 API(Next route handlers)를 같은 언어로 유지 |
| 도메인 모델 | `CauseTag`, `Breakpoint`, `Session` 등 타입으로 3축 진단을 명확히 표현 |
| 생태계 | 오디오·PWA·테스트(Playwright)·린트 도구가 성숙 |
| Agent/협업 | README·이슈·PR 워크플로와 맞는 일반적인 웹 스택 |

MVP 단계에서는 **Python/Kotlin 등으로 별도 백엔드를 두지 않는다.** STT 등이 필요해지면 API route에서 외부 서비스 호출로 시작.

### 2.1 왜 TypeScript인가 — 다른 언어와 비교

먼저 **이 앱이 언어에 요구하는 것**을 기준으로 본다.

| 요구 | 설명 |
|------|------|
| 풍부한 UI | 전사, 구간 선택, 태깅, 통계 — DOM/state가 많음 |
| 오디오 | 브라우저에서 재생·구간 반복이 1차 목표 |
| 1인·소규모 | 배포·유지보수 부담을 줄일 것 |
| 빠른 MVP | 습관 앱이므로 “듣기→진단→저장” 루프를 빨리 검증 |
| (선택) 서버 | STT/동기화는 나중; 처음엔 로컬 저장으로 충분 |

#### 후보 요약

| 후보 | 장점 | 이 프로젝트에서 채택하지 않은 이유 |
|------|------|-----------------------------------|
| **Java** | 타입 안정성, Spring 생태계, Android(Kotlin)와 인접 | **MVP가 웹·인터랙션 UI 중심**이라 서버(Spring) + 프론트(JS/TS) **이원화**가 먼저 듭니다. Android 네이티브만 Java/Kotlin으로 가면 PC·브라우저 학습 흐름을 따로 만들게 됩니다. 개인 1인 MVP에는 **시작 비용·UI 개발 속도**가 불리합니다. |
| **Vanilla JavaScript** | 빌드 없이 시작 가능, 런타임 의존성 적음 | 전사 하이라이트·상태(세션, 태그, 통계)가 늘면 **구조·버그**가 빨리 쌓입니다. TypeScript는 **도메인 타입**(단어/구조/소리)을 코드에 고정해 리팩터링을 안전하게 합니다. “vanilla”도 Vite+TS 조합이면 사실상 TS 쪽으로 갑니다. |
| **Python** | STT/NLP/스크립트, FastAPI·Django | **화면·오디오 UX**는 브라우저( JS 계열 )가 담당해야 합니다. Python만으로는 React급 UI를 대체하기 어렵고, 결국 **Python API + JS 프론트** 2스택이 됩니다. STT를 **자체 모델**로 깊게 할 때는 Python **마이크로서비스**를 *추가*하는 편이 낫고, MVP는 외부 API를 Next route에서 호출해도 됩니다. |
| **Kotlin / Swift** | 네이티브 앱 품질, 오디오·백그라운드 | Duolingo처럼 **매일 조금** 쓰려면 설치 장벽이 낮은 **웹/PWA**가 유리합니다. 네이티브는 2단계(UX 검증 후) 후보입니다. |
| **TypeScript** ✓ | UI+API 한 언어, 타입, 웹·PWA·테스트 도구 | 위 요구에 **가장 적은 스택 수**로 맞음. |

#### Java를 쓰는 경우가 더 맞는 때

- Android **네이티브 앱만** 목표로 할 때 (Kotlin이 더 일반적).
- 회사 표준이 Spring이고 **백엔드 팀**이 UI와 분리해 운영할 때.
- JVM 위 **장기 운영·대규모 API**가 핵심일 때 (MVP 학습 루프 검증 단계와는 거리 있음).

#### Python을 쓰는 경우가 더 맞는 때

- **자체 STT/발음 scoring 모델**을 repo 안에서 학습·서빙할 때.
- 콘텐츠 파이프라인(크롤링, NLP 배치)이 **제품의 중심**일 때.

→ 현재 README 목표는 **“어디서 이해가 끊기는지” UX**이므로, Python은 *필요해질 때* API 한 겹 추가하는 쪽이 맞다.

## 3. 어떤 프레임워크로 작업하는가 — **Next.js (App Router) + React**

| 이유 | 설명 |
|------|------|
| 풀스택 한 repo | 페이지 + 서버 API를 한 프로젝트에서 관리 |
| 배포 | Vercel 등으로 개인 프로젝트 배포가 단순 |
| 상호작용 UI | 전사 하이라이트, 구간 선택, 태깅에 React가 적합 |
| 점진적 확장 | 초기는 정적/클라이언트 위주 → 이후 DB·auth 추가 용이 |

### 3.1 왜 Next.js인가 — Vanilla JS / 다른 프레임워크와 비교

| 후보 | 장점 | 채택하지 않은 이유 (MVP 기준) |
|------|------|-------------------------------|
| **Vanilla JS + HTML** | 단순, 학습 곡선 낮음 | 라우팅·상태·컴포넌트 재사용을 **직접 설계**해야 함. MVP 이후 기능 추가 시 비용이 TS+React보다 커지기 쉽습니다. |
| **Vite + React (SPA만)** | 가볍고 빠른 dev server | API·배포·SEO(나중의 랜딩)를 **별도 서버**와 맞춰야 함. Next는 **한 repo**에 페이지와 route handler를 둡니다. |
| **Vue (Nuxt)** / **Svelte (SvelteKit)** | 훌륭한 DX, 풀스택 가능 | **선택 가능한 대안**입니다. 팀/개인 숙련도가 Vue/Svelte 쪽이면 Nuxt/SvelteKit으로 같은 문서 구조를 적용하면 됩니다. 기본안으로 Next+React를 둔 이유는 **예제·컴포넌트(shadcn)·배포(Vercel) 문서**가 많아 1인 MVP **막힘 구간이 적을 것**으로 보았기 때문입니다. |
| **Spring Boot + Thymeleaf** | Java 단일 | **인터랙티브 전사 UI**에는 서버 렌더링만으로는 개발이 느립니다. 결국 React 등 SPA를 붙이는 형태가 됩니다. |
| **Django templates + HTMX** | Python 친화, 서버 중심 | 구간 선택·오디오 sync 같은 **클라이언트 상태**가 많으면 HTMX만으로는 한계가 빨리 옵니다. |
| **Next.js + React** ✓ | 풀스택·배포·UI 라이브러리 | 위 MVP 요구에 맞춘 **기본안**. |

### 3.2 결정 한 줄 요약

> **브라우저에서 매일 쓰는 인터랙션·오디오 앱**을 **한 사람이 빠르게** 만들고, **나중에** STT/동기화를 붙이려면 **TypeScript + Next.js**가 스택 수와 UI 속도 면에서 균형이 좋다.  
> **Java/Python**은 그때그때 **추가 레이어**(Android 네이티브, ML API)로 두는 편이 낫다.

### 함께 쓰는 도구 (MVP 권장)

- **스타일/UI**: Tailwind CSS + shadcn/ui — 빠른 폼·버튼·다이얼로그.
- **클라이언트 저장**: IndexedDB (**Dexie**) — 서버 없이 세션·통계 유지.
- **오디오**: HTML5 `<audio>` + (필요 시) 구간 루프 UI; 2단계에서 wavesurfer.js 검토.
- **품질**: ESLint, Prettier, Playwright(E2E).
- **PWA**(선택): `next-pwa` 또는 manifest만 먼저 — “홈 화면에 추가”로 매일 접근.

### 의도적으로 MVP에서 미루는 것

- 네이티브 iOS/Android 앱 (웹 PWA로 먼저 검증).
- Supabase/Postgres (로컬 저장으로 진단 UX 검증 후).
- 실시간 STT (버튼 눌러 녹음·전송은 2단계).
